## Что изучено

Эталон — локальный
[windhawk-codex-lb-taskbar-dashboard](../../../windhawk-codex-lb-taskbar-dashboard/README.md),
метаданные мода версии 1.3. Его документация сообщает проверку с Windhawk 1.7.3;
FileVersion локального Windhawk также равен 1.7.3; это не подтверждает
совместимость нового проекта. [Результаты проверки среды](environment.md).

У исходного мода `mod.wh.cpp` содержит настройки, описание и entrypoints.
Реализация находится в `src/` в заголовках одной единицы трансляции, namespace
`codex_dashboard`. Windhawk компилирует вход через stdin из каталога Compiler;
в `@compilerOptions` указан абсолютный include-путь проекта.

| Часть исходного проекта | Наблюдаемая роль | Будущая работа |

Перенесены core, integration, UI, SemVer и основа release-cache; config и HTTP

`src/integration/lifecycle.h`. `accounts/`, старые session/usage и загрузчик
релизов не перенесены. `tests/` и `editor/` пока не созданы.

Независимые идентификаторы: `sub2api-taskbar-dashboard`, namespace
`sub2api_dashboard`, пользовательский кеш `Sub2ApiTaskbarDashboard`.
Отдельные XAML-имена `Sub2ApiDashboardWidget/Sub2ApiLatestUpdateIndicator`,
класс окна `Sub2ApiDashboardPopup`, сообщения WM_APP+0x532/0x533,
COM CLSID `A6E67E01-2E0C-4F58-A82F-7E196A986B43`, log/cache/mutex не
пересекаются с исходным модом. Зарегистрированное сообщение dispatch включает
Windhawk mod ID. `VisualDiagConnectionN` сохранено как имя системного протокола XAML.
Соседний `CodexLbDashboardWidget` только наблюдается: новый виджет размещается
слева от него с учётом ширины; события размера отзываются при cleanup.
Runtime-подтверждение одновременной работы остаётся в 05.02.

Не переносить `.git`, `.vs`, результаты сборок, пользовательский GitHub-кеш,
секреты, адрес сервера по умолчанию и абсолютные пути исходного проекта.
Не менять установку или компилятор Windhawk ради подготовки документов.

## Проверка будущей реализации

1. Статическая проверка потока данных, прав, парсинга, отмены, кеша и логов.
2. Compile-check с фактическим Windhawk toolchain, stdin/cwd/include и библиотеками.
3. Изолированные C++ проверки: формула, DTO, ошибки, сроки, SemVer и кеш.
4. С согласованным разрешением — реальная интеграция с сервером и визуальная
   приёмка в Windhawk, DPI, несколько мониторов, reload и одновременная работа модов.

У исходного harness режим `--offline` не показывает окна и не делает HTTP-запросы,
но использует Win32/GDI в памяти, временные файлы и именованный mutex. Обычный
режим создаёт локальный HTTP-сервер. Имя режима не заменяет проверку изоляции.
Запуск C++ компилятора/harness требует отдельного разрешения на точную команду.

В новом проекте ни один из этих запусков пока не выполнялся. Результат
подготовки документов не закрывает будущую проверку или визуальную приёмку.

## Фактическая проверка этапа 02

Статически прослежены entrypoints, пауза и завершение timer/manual work,
закрытие WinHTTP перед уничтожением async state, отписка watcher и UI callbacks,
уничтожение popup на его потоке и снятие регистрации класса. Ошибки отдельных
шагов cleanup логируются безопасным HRESULT и не пропускают остальные шаги.
Проверены включения и отсутствие циклов, независимость имён и отсутствие старой
авторизации/реального адреса. UI-код переиспользован с исключением badge
переавторизации; неизвестные проценты имеют -1, фиктивные аккаунты не создаются.

Бинарные результаты, кеши, .git/.vs, editor database и секреты исходного проекта
не копировались. Существующая .git нового проекта сохранена.
Сборка, harness, WinHTTP runtime, Windhawk/Explorer, DPI и визуальное совпадение
не проверены; статический разбор их не заменяет.
