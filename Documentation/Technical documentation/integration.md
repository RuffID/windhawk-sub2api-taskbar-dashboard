# Контракты sub2api

Основание: статическое чтение локального `../sub2api` 04.11.2026.
HTTP-запросы и чтение реквизитов Codex Desktop не выполнялись. Наличие этих
возможностей на конкретном сервере пока не подтверждено.

## Два разных вида доступа

[Маршруты gateway](../../../sub2api/backend/internal/server/routes/gateway.go)
подключают обычную API-key авторизацию к `/v1/usage`.
[GatewayHandler.Usage](../../../sub2api/backend/internal/handler/gateway_handler.go)
возвращает данные ключа: денежную квоту, ограничения ключа, подписку/баланс и
статистику использования. Это не список upstream-аккаунтов. Денежное недельное
ограничение ключа не является недельным лимитом аккаунта ChatGPT/Codex.
Контракта `account_pool_usage.secondary` исходного codex-lb здесь нет.

[Административная авторизация](../../../sub2api/backend/internal/server/middleware/admin_auth.go)
принимает администраторский `x-api-key` или администраторскую JWT-сессию.
Обычный пользовательский ключ не становится администраторским из-за смены
заголовка. Конкретный ключ пользователя не исследовался.

[Документация ключей](../../../sub2api/docs/admin-api-keys.md) и
[каталог прав](../../../sub2api/backend/internal/pkg/adminaccess/catalog.go)
описывают ограниченные администраторские ключи: операции и область аккаунтов
выдаются отдельно. Не нужно автоматически запрашивать полный доступ.

## Выбранное подключение нового мода

В основе этапа 02 администраторский ключ вводится непосредственно
в настройке Windhawk `adminApiKey` («Администраторский API-ключ»), по умолчанию
пустой. Клиент читает его через API настроек Windhawk и передаёт в `x-api-key`
только в запросах к настроенному серверу sub2api. Переменная окружения с именем
ключа, dashboard-login/cookie и доступ к настройкам Codex Desktop не нужны.

Пустой ключ не отправляется. При изменении настройки текущие операции отменяются,
а следующее обновление получает единый snapshot новых настроек. Значение ключа
не включается в UI-состояние карточек, сообщения ошибок, диагностические логи,
fixtures и файлы проекта. GitHub-запросы не получают этот заголовок.
Для подключения допускаются полный и ограниченный администраторские ключи.
Для ограниченного ключа с `policy.full_access=false` необходимы:
ресурсные права `accounts.read`, `accounts.identity.read`, `openai.quota.read`
для доступных OpenAI OAuth-записей и глобальное право `system.read`.
Для охвата всех разрешённых групп правило ключа должно действительно включать
эти группы; `all_groups` не включает записи без группы, для них отдельно
нужно `include_ungrouped`. Эти параметры не расширяются самим виджетом.
`accounts.usage.read` и `accounts.stats.read` для выбранного пути не нужны.
Настройки и транспорт реализованы; загрузчик аккаунтов ещё не подключён.

## Выбранный путь чтения

Все административные пути имеют префикс `/api/v1/admin`. Для будущего мода
выбран список `GET /accounts?platform=openai&page_size=100` со всеми страницами
и прямое чтение `GET /openai/accounts/:id/quota` для OAuth-записей. Параллелизм
клиентских запросов ограничивается; batch usage не является основным источником.
Карточки не-OAuth OpenAI-записей могут иметь `n/a`: метод quota отвергает их тип,
их денежные квоты не преобразуются в лимиты подписки.

Ниже также перечислены обследованные альтернативы; наличие строки не означает
включение маршрута в polling. На этапе 02 ни один маршрут ещё не вызывается.

| Путь | Данные и ограничения | Кандидат права ограниченного ключа |
| --- | --- | --- |
| `GET /accounts?platform=openai` | Страницы `items/total/page/page_size/pages`; есть фильтры `type` и `group`; нужно прочитать все страницы | `accounts.read`, дополнительные поля требуют отдельных прав |
| `GET /accounts/:id/usage` | Окна `five_hour`, `seven_day`, `thirty_day`, `utilization`, `resets_at`, статусы ошибок; поддерживает разные источники/режимы | `accounts.usage.read` |
| `POST /accounts/usage/batch` | `account_ids`, `force`; результат `usage` и `errors` по ID | `accounts.usage.read` |
| `GET /openai/accounts/:id/quota` | OpenAI `rate_limit`, primary/secondary windows, `rate_limit_reset_credits`, `fetched_at` | `openai.quota.read` |
| `POST /openai/accounts/:id/quota/refresh` | Запрос квоты с сохранением серверного snapshot; это не просто локальное чтение | `openai.quota.read` |
| `GET /system/version` | Версия в стандартном envelope, `data.version`; обработчик вызывает серверную проверку обновления | `system.read` |
| `GET /system/check-updates` | Состояние серверной проверки обновлений; отдельный контракт от codex-lb | `system.read` |

`scopedAdminAccountDTO` возвращает `id/name/platform/type/status/schedulable`,
срок действия и временные ограничения. При `accounts.identity.read` доступны
`credentials.email/plan_type/subscription_expires_at`, `extra.email`, `created_at`.
Это небольшая разрешённая проекция; её поля читаются явно, целиком credentials
в модель/логи не переносятся. При `accounts.usage.read` дополнительно возвращаются
только `extra.codex_usage_updated_at/codex_7d_used_percent/codex_7d_reset_at`.

В scoped-списке нет `parent_account_id`, `quota_dimension`, `error_message`,
`auto_pause_on_expired`. Нельзя переносить ожидания полного DTO на этот ответ.
Для shadow прямое quota-чтение проверяет право и самой записи, и её родителя;
также проверяется identity-право родителя перед выдачей upstream-идентификаторов.

Scoped batch usage принимает от 1 до 100 ID, предварительно проверяет всю
область, затем выдаёт `usage/errors` по ID. Один неавторизованный ID отклоняет
всю пачку. Успешная пачка всё равно может содержать ошибки отдельных записей.

## Окна, давность и устранение дублей

В `UsageProgress.utilization` передаётся использованный процент. В
`OpenAIRateLimitWindow.used_percent` также расход; остаток нужно вычислять.
Названия primary/secondary сами по себе не гарантируют недельную длительность:
проверяется `limit_window_seconds`: 604800 — недельное, 18000 — 5-часовое.
Месячное/другое длинное окно отображается отдельно и не попадает в weekly average.
`null`, отсутствие длительности или нечисловой/нефинитный процент не образуют
достоверное недельное значение. Расход сверх 100% даёт остаток 0%, отрицательный
расход считается некорректными данными. Остаток ограничивается диапазоном 0–100.
Истёкшее окно требует нового чтения, а не синтетического восстановления 100%.

`QueryUsage` делает GET к `/wham/usage`, выставляет `fetched_at` в Unix seconds
после успеха и дополнительно читает детали credits. Именно этот timestamp
используется для предела 900 секунд; повторный показ/ошибка HTTP его не обновляет.
После 900 секунд значение не участвует в среднем. При отсутствии timestamp
данные не выдаются за свежие. Ошибка чтения деталей Reset не отменяет успешную
квоту: неизвестный Reset остаётся неизвестным.

Выбор прямого quota обусловлен особенностями общего OpenAI usage:
`getOpenAIUsage` начинает с `UpdatedAt=now`, может сохранить старый `extra`
после неудачного probe, а затем создать `UsageProgress{Utilization:0}` ради
`window_stats`, даже если достоверного окна не было. Поэтому общий `updated_at`
и один `seven_day.utilization=0` недостаточны для доказательства свежести/100% остатка.
`source=passive` для OpenAI не работает: `GetPassiveUsage` поддерживает только
Anthropic OAuth/SetupToken и для остальных типов возвращает ошибку.

`scopedQuotaDTO` сохраняет `account_id`, `user_id`, email и plan только с
`accounts.identity.read`; для shadow сервис использует credentials родителя.
Будущий алгоритм группирует совпадающую полную пару `(account_id,user_id)`:
так одна upstream-идентичность не учитывается повторно, а одинаковый user_id
в разных workspace не сливается. Это соответствует разделению workspace/user
в `buildCodexStoredIdentityKeys`; группировка по одному email/name запрещена.
Для среднего берётся основной `rate_limit` одной идентичности, без повторного
прибавления `additional_rate_limits` Spark. Все карточки остаются видимыми.
При нескольких пригодных снимках выбирается наиболее свежий, при равенстве
времени — запись с меньшим ID для воспроизводимости. Отсутствие одного из двух
идентификаторов не позволяет доказать уникальность: запись остаётся с
неизвестными данными для среднего и признаком неполноты, без догадок по email.

Пригодность не приравнивается к `Account.IsSchedulable()`: тот исключает также
лимитированные записи. Для нашего среднего `status!=active` и ручное
`schedulable=false` исключают запись, а исчерпанный недельный лимит остаётся 0%.
Транспортный/авторизационный отказ не обновляет snapshot. Для оставленного
значения до 900 секунд показываются ошибка обновления и возраст; затем оно
исключается. Известные статусы недоступности остаются видны в карточках.

### Побочные эффекты серверного чтения

`RestrictedFromContext` возвращает restricted principal только при
`full_access=false`. В этой ветке `scopedOpenAIQuota(c,false)` не сохраняет
Reset/credits snapshots и не вызывает `NotifyOpenAIAutoResetCredit`.
Обычный full-access `QueryQuota` после чтения вызывает этот notify; при
включённой серверной автоматике он может привести к расходу Reset. Такое
поведение допустимо; полный ключ поддерживается наряду с ограниченным.
Один префикс `adm_sc_` не доказывает выключенный full_access.

Здесь notify означает внутреннюю передачу локального ID аккаунта в очередь
`OpenAIQuotaAutoResetService`, а не сообщение человеку или запрос сброса прямо
из GET. Worker читает аккаунт, проверяет включённый `auto_reset_credit_enabled`,
активность/доступность, заданные пороги расхода 5h/7d и наличие Reset credits.
При выполнении условий он вызывает `ResetCreditTargeted`, который может
израсходовать credit и восстановить лимит. Без включённой автоматики сам сигнал
её не включает и не означает выполненный сброс. Сигнал нужен для быстрой
проверки аккаунта вместо ожидания периодического обхода раз в минуту.
Scoped GET этого сигнала не отправляет; самостоятельную работу
уже включённого серверного автосброса виджет не отключает.
Клиент не включает и не перенастраивает эту автоматику и не вызывает отдельные
операции сброса. Различия серверных веток сохраняются, а не подавляются клиентом.

Источники: [очередь, worker и условия автосброса](../../../sub2api/backend/internal/service/openai_quota_auto_reset.go),
[настройки автоматики аккаунта](../../../sub2api/backend/internal/service/openai_quota_auto_reset_config.go).

Прямой GET всё же не обещает полного отсутствия серверных записей:
token provider при необходимости обновляет OAuth-токен, а Agent Identity
может восстановить task. Это штатное обеспечение авторизации upstream,
не расход попытки сброса. POST quota/refresh сохраняет snapshots и не нужен
выбранному клиенту. Период 60 секунд/ручное обновление наследуется от эталона;
прямые quota-запросы имеют timeout сервера до 20 секунд и выполняются с
ограниченной конкуренцией и общим клиентским deadline, без скрытых повторов.

Диагностика будущего клиента: `Account discovery failed` со статусом/номером
страницы, `Quota query failed` с локальным ID/статусом, `Snapshot incomplete`
с количеством пригодных/ожидаемых записей при смене состояния. Не писать
успешное обновление при отказе, не логировать upstream identifiers, email,
ключ или тело административного ответа. Это описание, события ещё не реализованы.

### Исключённая диагностика переавторизации

Scoped-список не выдаёт `error_message`, а scoped quota ошибки санитизируются.
`scopedUsageDTO` умеет отдавать `needs_reauth`, но OpenAI-путь `getOpenAIUsage`
его не устанавливает. Поэтому произвольный 502 нельзя превращать в badge
«Нужна переавторизация». В согласованную функциональность отдельный значок
и сообщение переавторизации не входят. Клиент показывает доступный общий
статус/ошибку без попытки восстановить этот диагноз; соответствующее поле
в нормализованной модели и renderer не требуется. Это исключение из эталона,
а не незавершённая работа. Серверная доработка не требуется.

`Reset (N)` должен использовать количество доступных credits и ближайший
`expires_at`. Маршруты `reset-quota`, восстановления аккаунта, смены статуса,
обновления и перезапуска сервера не входят в нужный моду путь и не вызываются.

## Версии

[UpdateService](../../../sub2api/backend/internal/service/update_service.go)
использует `Wei-Shaw/sub2api`, он выбран и для нового мода. `GET /system/version`
возвращает `data.version`; `GET /system/check-updates` —
`data.current_version/latest_version/has_update/cached/warning/build_type`.
Taskbar-индикатор получает `has_update` сервера, popup независимо проверяет
официальные опубликованные релизы, включая prerelease. Сервер кеширует свою
проверку 1200 секунд; клиентский GitHub-кеш сохраняет отдельный часовой минимум.
`GetVersion` сам вызывает `CheckUpdate(false)`, поэтому чтение версии тоже
может вызвать серверный запрос GitHub, но не установку обновления.

## Граница работ

Владелец сервера — соседний проект sub2api; новый мод владеет чтением,
нормализацией и отображением разрешённых данных через существующий административный
API. Серверные правки и расширение доступа обычного ключа вызова моделей
для выбранного подключения не требуются и в этом плане не поручены.

## Реализация основы этапа 02

- [Настройки](../../src/config/settings.h): `sub2apiUrl` и `adminApiKey`
  по умолчанию пустые; interval 60 секунд, timeout 30 секунд, границы
  30–2147483 секунд. URL нормализуется без конечного слеша. Допускается HTTP(S)
  с путевым префиксом reverse proxy; query, fragment, userinfo и управляющие
  символы запрещены. Ключ проверяется только как безопасное значение заголовка,
  без предположений о full_access по префиксу.
- [Транспорт](../../src/network/http.h): `Sub2ApiGet` добавляет
  `/api/v1/admin` и относительный ресурс; только GET, `x-api-key`.
  Успех требует HTTP 2xx, JSON-объект с числовым целым `code=0`,
  строковым `message` и объектом `data`. Не-JSON, повреждённый envelope,
  ненулевой code и HTTP 401/403/429/5xx возвращают отказ без повторов/login.
  Серверные message/reason/body не передаются в UI или логи.
- Каждый запрос ограничен собственным timeout и переданным deadline обновления,
  максимум 4 MiB и строгим UTF-8. Тот же deadline передаётся всем запросам
  будущего обновления. Чтение/ожидания прерываются по общему событию отмены.
  Закрытие запроса ожидает финальный callback до уничтожения буфера и контекста.
- Redirects, cookies и автоматическая авторизация WinHTTP отключены.
  `GitHubGetReleases` имеет фиксированный публичный URL `Wei-Shaw/sub2api`,
  не принимает Settings или ключ; HTTP-вызов получает пустую авторизацию.
  Планирование и обработка версий остаются этапу 04.
- [Lifecycle](../../src/integration/lifecycle.h) при смене настроек сначала
  сигнализирует отмену, завершает timer/manual callbacks, затем меняет snapshot.
  Событие сбрасывается только после завершения старой работы. Перед публикацией
  проверяется отмена; неудачная смена оставляет обновления остановленными.
- [Runtime](../../src/integration/runtime.h) пока публикует только состояние
  подключения, пустые аккаунты, неизвестный процент и отсутствие времени успеха.
  `Sub2ApiGet` и `GitHubGetReleases` из runtime не вызываются. Это готовая
  граница транспорта, а не подтверждённое подключение к серверу.

Контракт envelope сверён с
[response.go](../../../sub2api/backend/internal/pkg/response/response.go),
авторизация — с указанным выше middleware. Выполнен статический разбор веток.
Компиляция и транспортные проверки (включая задержки, отмену, большие ответы,
полный/ограниченный ключ и префикс reverse proxy) не запускались; остаются для 05.01/05.02.
